🚀 AgenticUPI

A Production-Grade Distributed Payment Switch for Untrusted AI Agents

Executive Summary

AgenticUPI is a complete, zero-mock system demonstrating Principal/Staff-level expertise in:

  • High-Concurrency Financial Systems — Designed for 10K TPS with strict ACID guarantees
  • Untrusted Boundary Design — Cryptographic HMAC validation, payload hashing, idempotency
  • Distributed Systems Patterns — Two-phase velocity reservations, fail-closed semantics, Redis/DB coordination
  • Production Architecture — Double-entry ledgers, transactional outbox relays, pessimistic kill-switches
  • Full-Stack Implementation — Java Spring Boot backend, Python FastAPI SDK, Angular RxJS UI

The Problem

Allow autonomous LLM agents (ChatGPT, Claude, custom models) to execute UPI payments on behalf of users, while maintaining:

  • Zero double-debits — Even on network timeouts or retries
  • Real-time mandate revocation — Users can kill-switch an agent's access instantly
  • Untrusted input handling — Raw cryptographic validation, structured Pydantic constraints
  • 10K TPS throughput — Without lock contention or connection pool exhaustion

Key Technical Decisions

1. Raw-Byte HMAC Signing (Not JSON Canonicalization)

Interview Signal: Proves you understand multi-language integration failures at scale.

Java's Jackson and Python's json.dumps serialize differently (key order, float precision). Solution: Sign the exact HTTP request bytes.

signature_base = SHA256(raw_body_bytes) + "." + timestamp + "." + idempotency_key + "." + agent_id

2. Idempotency Key Lifecycle (UUID Outside Retry Loop)

Interview Signal: This catches most engineers. Generating UUID inside a retry loop = double debits on timeout.

Solution: Generate idempotency_key ONCE before tenacity wrapper. Pass the same key to all retries.

3. Two-Phase Velocity Reservations

Interview Signal: Cache acceleration without sacrificing durability.

Phase 1: Redis Lua creates PENDING reservation. Phase 2: DB transaction commits. Phase 3: POST-COMMIT hook finalizes Redis reservation. If DB rolls back, Redis is cleared. User never loses quota.

4. Fail-Closed Mandate Kill-Switches

Interview Signal: Security-first architecture.

Revocation updates DB FIRST (authority), then Redis tombstone (acceleration). If cache is down, DB blocks the payment anyway.

5. SKIP LOCKED Outbox Relays

Interview Signal: Horizontal scaling without lock contention.

Multiple workers poll with FOR UPDATE SKIP LOCKED. Claim rows quickly, release locks, publish to Kafka outside transaction.

Interview Talking Points

Opening (2 minutes)

"AgenticUPI is a distributed payment switch I built to solve a specific problem: how do you let untrusted LLM agents execute financial transactions without risking double-debits, lost quota, or race conditions? The system achieves 10K TPS with zero data loss, implements cryptographic boundary validation, and demonstrates a clear separation between the untrusted Zone 0 (the agent), the authoritative Zone 1 (the backend), and the control Zone 2 (the user dashboard)."

Technical Depth (5-10 minutes)

Walk through the three zones:

  • Zone 0 Problem: "An LLM agent generates a payment intent. I can't trust its input. Solution: Strict Pydantic validation + raw-byte HMAC signing. The agent signs the exact HTTP body bytes, not a reconstructed JSON string."
  • Zone 1 Problem: "The backend receives a signed request. It must verify the signature, check velocity limits, and commit money without ever double-charging, even on retries. Solution: Redis Lua for fast velocity checks, DB for authority, post-commit hooks to synchronize cache state with DB commits."
  • Zone 2 Problem: "Users need to revoke an agent's access instantly. The UI must never lie and say 'revoked' before the DB confirms it. Solution: Pessimistic revocation, no optimistic UI updates for kill-switches. The backend updates the DB first, then the UI refreshes."

Architecture Decisions (3-5 minutes)

Hit the highest-signal points:

  • Raw-Byte HMAC: "I chose this over JSON canonicalization because at scale, Java/Python/Go serialize differently. Raw bytes guarantee perfect signature matching across languages."
  • Two-Phase Velocity: "Redis is not the source of truth; MariaDB is. The Lua script creates a pending reservation, the DB transaction commits, and a Spring post-commit hook finalizes the reservation. This way, if the DB rolls back, the user doesn't permanently lose their velocity quota."
  • SKIP LOCKED Outbox: "Multiple backend pods poll the outbox table for events. Using FOR UPDATE SKIP LOCKED means they never fight for locks. Each pod claims different rows, publishes to Kafka outside the DB transaction, then acknowledges success. This scales to 10K TPS."

Interview Challenge (2-3 minutes)

"Walk me through what happens if an agent's payment request times out on the wire. How do we know we haven't double-charged?"

Expected Answer: "The idempotency key is generated once, before the retry loop. If the request times out, the retry uses the exact same key. The backend's idempotency logic first checks Redis (fast path), then the database (UNIQUE constraint). If the idempotency key already exists with a matching request hash, we return the cached result. If the hash differs, we reject as a conflict. This is why the idempotency key must be stable across retries."
