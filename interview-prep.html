🚀 AgenticUPI Interview Prep

Principal/Staff-level system design for untrusted LLM payment agents

System Overview

What is AgenticUPI?

A production-grade distributed payment switch that safely executes UPI payments on behalf of untrusted LLM agents (ChatGPT, Claude, custom models) at 10K TPS with zero data loss.

Interview Signal: This system demonstrates Principal/Staff expertise in financial systems, distributed architectures, and untrusted boundary design — exactly what Navi/PhonePe need.

The Core Problem

How do you allow autonomous AI agents to execute payments while maintaining:

  • Zero double-debits — Even on network timeouts and retries
  • Real-time mandate kill-switches — Users revoke agent access instantly
  • Untrusted input validation — Cryptographic verification, not trust
  • High throughput — 10K TPS without lock contention

Three Trust Zones

🤖 Zone 0: Untrusted

Python FastAPI agent SDK. LLM generates payment intents, signs with raw-byte HMAC-SHA256. We assume this is compromised.

💳 Zone 1: Core Authority

Java Spring Boot payment switch. MariaDB is the absolute truth. Redis accelerates, but doesn't decide. All financial decisions live here.

📊 Zone 2: Control Plane

Angular RxJS dashboard. Users manage and revoke mandates. Pessimistic UI (no optimistic updates for kill-switches).

Resume Bullet

Designed and implemented a distributed payment switch (AgenticUPI) to safely execute payments on behalf of untrusted LLM agents at 10K TPS with zero data loss. Engineered 2-phase Redis Lua velocity reservations synchronized durably with MariaDB via Spring post-commit hooks to prevent permanent quota loss on DB rollbacks. Implemented raw-byte HMAC-SHA256 verification eliminating JSON canonicalization vulnerabilities across Python-Java integration. Built high-throughput Kafka outbox relays using FOR UPDATE SKIP LOCKED and Claim-Publish-Ack patterns to scale horizontally without lock contention. Demonstrated fail-closed security with pessimistic mandate kill-switches, timestamp replay windows, and idempotency key lifecycle management.

Technical Deep Dive (5-10 minutes)

Walk through each zone systematically.

Zone 0: Untrusted Agent (Python FastAPI)

The Problem
An LLM agent generates a payment intent. I can't trust its input. The agent could be compromised, hallucinating, or malicious.
The Solution
Raw-byte HMAC-SHA256 signing. The agent signs the exact HTTP request bytes, not a reconstructed JSON string. Why? Because Java's Jackson and Python's json.dumps serialize differently (key order, float precision, whitespace). If we signed the canonical JSON, a multi-language system would never match signatures.
Implementation
body_hash = SHA256(raw_body_bytes)
signature_base = body_hash + "." + timestamp + "." + idempotency_key + "." + agent_id
signature = HMAC-SHA256(shared_secret, signature_base)
The backend verifies this signature BEFORE deserializing any JSON.
Idempotency Key Lifecycle (Critical!)
Generate the UUID ONCE, BEFORE the tenacity retry wrapper. Pass the same key to all retries. This prevents double-debits on timeouts. If you generate UUID inside the retry loop, each timeout creates a new key, and the backend treats it as a new payment.

Zone 1: Core Authority (Java Spring Boot)

The Problem
The backend receives a signed request. It must verify the signature, check velocity limits, and commit money without ever double-charging, even on retries. Database must be the source of truth. Redis accelerates but doesn't decide.
Two-Phase Velocity Reservations
Phase 1 (Redis Lua): Create a PENDING reservation with timestamp-based scoring. This is fast, non-blocking.
Phase 2 (DB Transaction): Execute the payment in MariaDB with pessimistic locks. If the DB commits, the Redis reservation is durable — the agent has used their quota.
Phase 3 (POST-COMMIT Hook): Spring TransactionSynchronizationManager finalizes the Redis reservation. If the DB rolls back, the hook clears the reservation — the user doesn't permanently lose quota.
Why This Matters
If you only use Redis for velocity, a DB rollback leaves a stale reservation consuming quota forever. If you only use the DB, you're blocked on DB latency (slow). This two-phase design gives you speed + durability.
Idempotency Verification
Calculate request_hash = SHA256(raw_body_bytes). Store "hash:IDEMPOTENCY_KEY:STATUS:PAYLOAD" in Redis with 48-hour TTL. On collision, compare hashes. If they match, return cached result. If they differ, reject with IDEMPOTENCY_CONFLICT error.
Double-Entry Ledger
Every payment creates two ledger entries: DEBIT from payer, CREDIT to payee. This ensures balanced books and enables reconciliation. Prevents silent corruption.

Zone 2: Control Plane (Angular RxJS)

Pessimistic Mandate Revocation
User clicks "Revoke Agent Access". The UI does NOT immediately show "Revoked". Instead: (1) Backend updates the DB, (2) Sets a Redis tombstone, (3) UI polls and refreshes. Only after the backend confirms does the UI update. This prevents lying to users about kill-switches.
RxJS Streams
Mandate service exposes mandates$: Observable<Mandate[]> using BehaviorSubject trigger. Component subscribes with async pipe, automatic unsubscribe on destroy. No manual subscriptions, no memory leaks.
OnPush Change Detection
Every component uses ChangeDetectionStrategy.OnPush. Change detection runs only when @Input changes or an observable emits. This scales to hundreds of components without performance degradation.

Key Technical Decisions

1. Raw-Byte HMAC (Not JSON Canonicalization)

Why This Signals Expertise
Most engineers assume JSON canonicalization is the solution. But at scale, different languages serialize differently. This shows you've debugged multi-language integration failures and learned the hard way.

2. Two-Phase Velocity (Not Just Redis, Not Just DB)

Why This Signals Expertise
Cache-aside is easy. Cache-first is risky. This pattern combines speed + durability without sacrificing either. Shows deep understanding of distributed systems trade-offs.

3. Claim-Publish-Ack Outbox (Not One-Shot Publish)

Why This Signals Expertise
Three-step pattern: (1) Claim rows from outbox with FOR UPDATE SKIP LOCKED, release lock, (2) Publish to Kafka outside the transaction, (3) Ack success in a separate transaction. Enables horizontal scaling without lock contention. Most engineers try to publish inside the transaction and hit timeouts.

4. Pessimistic Mandate Revocation (Not Optimistic UI)

Why This Signals Expertise
For kill-switches, never lie to users. Pessimistic revocation means: update DB first, then UI reflects reality. Shows you prioritize safety over perceived responsiveness.

5. Fail-Closed Architecture

Why This Signals Expertise
If Redis is down, payments still work (hitting DB directly). If Kafka is down, outbox events queue in DB until Kafka recovers. If any cache is stale, the DB is the source of truth. This is financial systems thinking.

Common Interview Challenges & Answers

❓ "An agent's payment request times out on the wire. How do we know we haven't double-charged?"
The idempotency key is generated once, before the retry loop. If the request times out, the retry uses the exact same key. The backend's idempotency logic first checks Redis (fast path) — if the key exists with a matching request hash, we return the cached result. If the hash differs, we reject as a conflict. This is why the idempotency key must be stable across retries. The database has a UNIQUE constraint on (idempotency_key, agent_id), so even if Redis is down, the DB prevents double-debits.
❓ "What happens if the backend crashes after reserving velocity but before committing the payment?"
The velocity reservation is PENDING in Redis. The DB transaction never committed, so there's no ledger entry. On backend restart, we don't finalize the reservation. The Redis entry expires after 24 hours. The user doesn't permanently lose quota. This is why the two-phase design matters — if we only used Redis, the reservation would stick forever.
❓ "What if a user revokes an agent's mandate but a payment is in-flight?"
Mandate revocation updates the DB immediately, setting status=REVOKED. If a payment is in-flight, it will check the mandate status before creating the ledger entry. If the mandate is revoked, the payment is rejected. The mandate tombstone in Redis ensures the check is fast. If the agent tries to retry the payment, it gets rejected again.
❓ "How do you prevent an agent from retrying forever to exploit a race condition?"
The idempotency key has a 48-hour TTL. After 48 hours, if the agent retries with the same key, it's treated as a new transaction (quota check, mandate check, etc. run again). This bounds the retry window while giving the agent enough time to recover from transient failures. We also track failed attempts and can throttle or block an agent after repeated failures.
❓ "Why not use optimistic locking instead of pessimistic?"
Optimistic locking (versioning + retry on conflict) works well for read-heavy, low-contention systems. But payment velocity is high-contention — many agents trying to hit the same quota simultaneously. Pessimistic locking (SELECT ... FOR UPDATE) wins here. We do use optimistic conflict detection as a fallback — if the version check fails, we know the DB changed and can retry or reject gracefully.
❓ "What's the latency profile? Can we hit 10K TPS?"
Redis velocity check: ~1ms. DB pessimistic lock + insert ledger entries + commit: ~5-10ms. Kafka publish (async, outside transaction): ~2-5ms. Total: ~10-15ms p95. At 10K TPS, we're processing ~100-150 requests per millisecond per pod. With connection pooling (50 max connections) and multiple pods, we scale horizontally. Lock timeouts are rare because we hold locks briefly and use SKIP LOCKED for batch claims.
❓ "How do you handle KMS decryption for HMAC secrets? Isn't that a bottleneck?"
We cache decrypted secrets in memory with a 1-hour TTL and automatic refresh on expiry. KMS decryption happens once per hour per credential, not per request. This gives us the security of envelope encryption without the latency penalty.
❓ "What would you do differently if you built this again?"
[This is a good opportunity to show humility and deeper thinking. Examples:]
• I might use optimistic locking on mandates (lower contention) instead of pessimistic, with conflict resolution.
• I'd add circuit breakers for Redis/Kafka failures earlier — current design works but could fail-over faster.
• I'd instrument velocity differently — current bucketing (time-based) works, but I'd explore token-bucket algorithms for smoother rate limiting.
• I'd build an audit log from the start, not retrofit it later.
